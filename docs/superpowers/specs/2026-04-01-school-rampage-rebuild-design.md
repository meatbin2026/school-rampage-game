# 校园暴走半重建设计稿

**日期：** 2026-04-01

## 目标

在保留当前已实现玩法与内容资产的前提下，对项目进行一次半重建：

- 保留核心割草战斗、角色、武器、Boss、成长、成就、存档与移动端支持
- 重做首页、战前整备、局内 HUD、结算页与整体视觉风格
- 回归常规割草玩法：不做主动技能系统，主副武器自动攻击
- 道具仅作为局内随机拾取、限次使用的战斗资源
- 将单体 `js/game.js` 演进为可长期维护的模块化结构

## 产品方向

### 产品定位

“热血街机校园”风格的构筑驱动型割草生存游戏。

它不是纯街机启动页，也不是重养成大厅，而是让玩家在开战前迅速理解：

- 角色是谁
- 当前主副武器是什么
- 这一局将围绕什么 Build 展开

### 核心体验

1. 开局前 15 秒内完成角色与 Build 理解
2. 开局后 5 秒内进入稳定自动攻击与走位循环
3. 每次升级和掉落都清楚地服务武器构筑
4. Boss、道具、升级与武器成长共同制造局内节奏变化

## 玩法边界

### 保留

- 角色选择
- 主副武器系统
- 自动攻击
- 随机升级选项
- 道具掉落
- 波次推进
- Boss 战
- 武器精通
- 成就 / 称号
- 本地存档
- 移动端控制

### 移除或不再扩展

- 主动技能按键系统
- 战前道具装配
- 复杂动作游戏式连招交互
- 首页上过重的养成大厅信息

### 新规则定义

- 武器：主副武器均为自动攻击，负责 Build 差异和战斗表达
- 道具：局内随机拾取，有限次数，偏救场、爆发或资源转换
- HUD：突出武器链、波次、Boss、状态与拾取反馈，不服务技能按键

## 视觉方向

### 视觉关键词

- 热血
- 街机
- 漫画
- 校园恶搞
- 高对比
- 粗描边
- 大色块
- 速度线

### 设计选择

采用“漫画街机混合风”而非纯像素街机或校园海报风。

原因：

- 保留热血街机的高能量和辨识度
- 比纯街机风更适合现代 HUD 可读性
- 更适合承载角色卡、武器卡、Build 卡和结算信息
- 在移动端也更容易维持层级清晰

## 页面结构

### 1. 首页大厅

职责：

- 进入游戏的主入口
- 展示角色身份与最近 Build
- 提供图鉴、成就、记录入口

布局：

- 左侧：当前角色与风格海报
- 中央：最近 Build、模式入口、继续战斗
- 右侧：成就进度、武器图鉴摘要、版本亮点

### 2. 战前整备

职责：

- 显示角色定位
- 选择或确认主副武器
- 展示天赋摘要
- 给出当前 Build 风格与风险提示

布局：

- 左：角色卡
- 中：主武器 / 副武器 / 被动摘要
- 右：Build 描述、成长倾向、适合场景
- 底部：开始战斗

### 3. 局内战斗

职责：

- 呈现战场信息
- 支持自动攻击、拾取、升级与道具使用
- 在 Boss 阶段清晰提升信息密度

布局：

- 顶部：波次、时间、Boss 阶段
- 左上：血量、经验、怒气、角色状态
- 底部中间：主副武器、被动与 Build 标签
- 右下：局内道具槽
- 右上：小地图 / 暂停 / 设置

### 4. 结算页

职责：

- 回顾这局的 Build
- 呈现成长、解锁和统计
- 驱动再来一局

布局：

- 左：本局战绩
- 中：Build 复盘与关键武器
- 右：精通 / 成就 / 解锁变化

## 系统设计

### 场景系统

重建为显式场景切换：

- `home`
- `loadout`
- `battle`
- `results`

场景拥有独立 UI 和生命周期，不再让一个 HTML 页面直接塞满所有状态。

### 状态系统

将状态分为三层：

- `metaState`：角色、武器解锁、成就、称号、排行榜、设置
- `runState`：当前局角色、武器、掉落、波次、Boss、战场实体
- `uiState`：当前页面、弹窗、提示、过场、选中项

### 数据层

把纯数据表从大文件中拆出：

- 角色
- 武器
- 敌人
- Boss
- 道具
- 升级项

### 战斗系统

战斗系统按职责拆开：

- 玩家系统
- 武器发射系统
- 子弹与命中系统
- 敌人与 Boss 系统
- 掉落系统
- 波次系统
- 状态效果系统
- 结算系统

### UI 系统

界面按场景拆分：

- 首页视图
- 整备视图
- HUD 视图
- 升级弹窗
- 暂停与设置
- 结算视图

## 迁移策略

### 原则

不在第一步直接硬拆 `js/game.js` 成很多脆弱碎片。

先建立新的应用外壳和目录结构，再把旧战斗逻辑逐步迁移进去。

### 阶段

1. 建立新的模块化入口、CSS 变量和页面壳子
2. 迁移数据定义与全局状态容器
3. 将旧战斗内核接到新的 battle scene
4. 逐步把战斗逻辑拆出独立系统
5. 用新 UI 替换旧 DOM 逻辑

## 风险与控制

### 主要风险

- 一次性改太大导致无法游玩
- UI 重构时把旧逻辑事件链打断
- 模块拆分期间状态同步混乱

### 控制手段

- 先做可运行的新壳子，再迁移功能
- 保留 battle scene 的旧逻辑桥接层
- 每次只迁移一类系统，避免全量改写
- 优先保证“可打开、可开局、可打一局”

## 成功标准

- 首页、整备页、局内 HUD、结算页全部换成新结构
- 游戏仍可完整开局、升级、打 Boss、结算
- 武器与道具的身份更清晰
- `js/game.js` 不再承担全部产品职责
- 后续继续迭代新武器、地图、模式时，不再依赖单文件硬堆
